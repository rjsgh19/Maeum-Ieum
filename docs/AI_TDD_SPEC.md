# AI TDD·검증 스펙

이 레포에 테스트 러너가 없을 수 있으므로, AI는 **(A) 자동 테스트**와 **(B) 수동 검증 시나리오**를 상황에 맞게 조합한다.

---

## 1. 원칙

1. **행동이 명확한 요구** → 아래 **Red → Green → Refactor** 사이클을 따른다.  
2. 테스트는 **사용자 가치·회귀 방지**에 연결되게 이름과 설명을 짓는다.

### 1.1 Red — Green — Refactor (필수 워크플로)

| 단계 | 할 일 |
|------|--------|
| **Red** | 수용 기준을 반영한 **테스트(또는 재현 시나리오)를 먼저** 둔다. 구현 전에 **실패**함을 확인한다 (자동 테스트면 테스트 러너가 빨간색, 수동이면 의도적으로 실패·미구현 상태 재현). |
| **Green** | 그 테스트/시나리오를 **통과시키는 최소한의 구현**만 한다. 과도한 일반화·부가 기능은 넣지 않는다. |
| **Refactor** | 동작은 그대로 두고 **가독성·중복 제거·구조 정리**를 한다. 이 단계 끝에 **테스트/시나리오가 여전히 통과**해야 한다. |

프론트가 단일 HTML 등으로 자동 테스트가 어려우면, Red/Green은 **「실패 재현 단계 → 최소 수정으로 통과」**로 치환한다 (§3).

---

## 2. 백엔드 (FastAPI)

- **권장**: `pytest` + `httpx` `AsyncClient` 또는 `TestClient`로 엔드포인트 테스트.  
- 테스트 파일 예: `tests/test_<feature>.py` (프로젝트 루트에 `tests/` 도입 시).  
- DB가 필요하면 **테스트 더블·스텁·로컬 SQLite(가능할 때)** 등으로 외부 의존을 줄인다.  
- 아직 `tests/`가 없으면: **이번 작업에서 테스트 디렉터리를 추가해도 되는지** Planner에 명시하고, 추가 시 `pytest` 의존성을 `requirements`에 반영한다.

### 산출물 형식

```text
## TDD 계획
- 테스트 파일: tests/...
- 케이스 1: ... → 기대 HTTP / JSON ...
- 케이스 2: ...
```

---

## 3. 프론트엔드 (`static/index.html`)

- 단일 HTML이면 **E2E 도구 없이** 다음을 TDD 대체로 쓴다:  
  - **수동 시나리오** (Given/When/Then)  
  - **콘솔·네트워크 탭**에서 확인할 요소  
- 복잡한 순수 함수(포맷터 등)는 **JS 단위 테스트 도구 도입 전제**가 있을 때만 분리·테스트를 제안한다.

### 산출물 형식

```text
## UI 검증 시나리오
1. ... 화면 열기 → ... 클릭 → ... API 호출 확인
2. ...
```

---

## 4. DB·쿼리

- 스키마 변경 시: **마이그레이션 적용 전후**로 동일 시나리오를 실행해 데이터 무결성을 확인하는 항목을 수용 기준에 넣는다.  
- SQL은 **읽기 전용 검증 쿼리** 예시를 Planner/TDD 섹션에 적을 수 있다 (실데이터 금지).

---

## 5. 완료 정의 (Definition of Done)

- [ ] Planner 수용 기준과 TDD/시나리오 항목이 **모두 충족**되었거나, **의도적으로 제외**된 항목이 이유와 함께 기록됨.  
- [ ] 회귀 가능성이 있는 경로를 **최소 1회** 재확인함.  
- [ ] 새 코드에 **민감 정보 하드코딩**이 없음.

---

## 6. AI 출력 순서 (Red → Green → Refactor와 대응)

1. **Red**: 실패하는 테스트 작성·실행 확인, 또는 실패 재현 시나리오 확정  
2. **Green**: 최소 구현 후 테스트·시나리오 통과 확인  
3. **Refactor**: 구조 개선 후 **다시** 통과 확인 (회귀 없음)

이 순서를 지키기 어려운 긴급 핫픽스는 Planner에 **예외 사유**를 한 줄 남긴다.
